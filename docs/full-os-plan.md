# Plan: booting full macOS (not Recovery) on the Pixel 8a

Status as of Nov 6, 2026 (historical: this plan was carried out; full macOS now boots to the desktop).
Base: macOS 26.5 (25F71), macOS-ForSheng kernel with the akita patches, `live3`/`live4` image.

## What we had
- In `userdata` (4-window manifest): `OS` (BaseSystem), `ISC`, `MacOS` (full system, APFS container with a single volume
  "Macintosh HD", UUID `47719F50-5527-44A3-9F59-8170528D8C14`, **unsealed and with no volume group**) and `SystemOS`
  (sealed cryptex, container UUID `39D59E60-…`).
- Full-system binaries pass AMFI and the shared cache maps: the kernel accepts it from the root volume or from
  `/System/Volumes/Preboot/Cryptexes`.
- The 5 software-drawing policies, already located in the full cache: `config/akita-fullos-ui-pages.json`.
- The kernel patch that leaves non-Recovery pages untouched.
- Live control: UDP log, keyboard/mouse, screenshots and SSH.

## How Recovery boots (macOS-ForSheng)
- ADT `/chosen`:
  - `osenvironment = recoveryos`;
  - `boot-uuid` and `apfs-preboot-uuid` = BaseSystem's UUID;
  - `secure-boot-hashes/system-volume-auth-blob` = BaseSystem's *root hash* (authenticated root);
  - `asmb/lp-sip0 = 0`.

  Generated by `scripts/native_devtree.py: configure_native_text_state` from `platform/akita/package-akita-macos.py`.
- NativeUfs (Recovery mode) publishes the windows as disks; the root is chosen by UUID.
- The `/System/Volumes/Data` tmpfs is mounted by Recovery's userland, not the kernel.

## What changes for full macOS
1. **Root:** `boot-uuid` = "Macintosh HD".
   - Either **authenticated**: seal the volume (`apfs_sealvolume`, from the restore ramdisk) and use the IPSW's `root_hash`.
   - Or **unauthenticated**, since SIP is disabled (`lp-sip0`). Check what the kernel requires without `system-volume-auth-blob`.
2. **SystemOS cryptex before launchd:** launchd and all of userland need the cryptex's dyld cache.
   - On a Mac launchd grafts it with `graftdmg` and an img4 ticket; there is no ticket here.
   - Option A (kernel, UniXNU style): before `load_init_program`, mount the SystemOS volume over
     `/System/Volumes/Preboot/Cryptexes/OS` (with a tmpfs on `/System/Volumes/Preboot` to create the path).
   - Option B (image): copy the cache into the system volume at `/System/Library/dyld` (dyld and the kernel accept that path).
     Requires rebuilding the `MacOS` window owned by root, so it needs sudo on the Mac.
3. **Data volume:** APFS mounts Data by role inside the system's volume group (`KERNEL_MOUNT_DATAVOL`, `VFSIOC_MOUNT_BYROLE`).
   Our image has no group.
   - Option A: a tmpfs on `/System/Volumes/Data` mounted by the kernel before launchd (as Recovery does from userland). Check
     whether the *firmlinks* (`/Users`, `/private/var`, `/Library`…) work without a group.
   - Option B: rebuild the container with a Data volume (role D) grouped with the system and a window with a volatile RAM
     *overlay* like ISC's.
4. **User and Setup Assistant:** pre-create a user (`/private/var/db/dslocal/nodes/Default/users/*.plist`) and
   `/private/var/db/.AppleSetupDone`, or let Setup Assistant run.
5. **Software drawing:** enable the `akita-fullos-ui-pages.json` table in the kernel so Recovery's and the full system's rules
   coexist. Today the first rule with the same offset wins; `return` must become `continue` on a mismatch.
6. **ADT and boot-args:** no `osenvironment=recoveryos`; drop Recovery-only patches (Springboard, `recoveryosd`); keep
   `native-gop-display`, input, the USB gadget and the log.

## First proposed experiment (RAM only, no flashing)
Image with `boot-uuid` = "Macintosh HD", a kernel that mounts SystemOS and a tmpfs for Data before launchd, and the UDP log.
Goal: see in the log how far the full system's launchd gets (loginwindow, WindowServer) and which services fail. Then Setup
Assistant or the pre-created user.

## Known risks
- RAM: XNU only used 4 GB (`owned_memory`). Raising it would help full macOS a lot (done in Nov 2026: 5.26 GiB).
- Services that expect Mac hardware (Secure Enclave, `mobileactivationd`, Wi-Fi and Bluetooth) may block loginwindow.
- Slowness: the first launch of each app takes minutes (font scan, CPU).
